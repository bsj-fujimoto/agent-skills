# claude-design-live-spec — Claude Design画面のライブ実測仕様書

Claude Designプロジェクト内の`.dc.html`画面に対して、**採番チップ+破線枠の注釈**と**要素テーブル(#/要素/種別/動作/テキスト)**を持つ「仕様書ページ」を追加する手順。

最大の特徴: 注釈の位置・サイズはスクリーンショットへのヒューリスティックな当てはめではなく、**同じプロジェクト内の対象画面をiframeでライブ表示し、その中の実DOM要素を`getBoundingClientRect()`で実測**して描く。そのため対象画面のレイアウトが変わっても、仕様書ページを再生成せずに追従する。

## 使う場面

- 「この画面のUIに番号を振って、それぞれが何をするものか説明して」
- 「画面仕様書を作って」「クリックすると何が起きるか・テキストが静的/動的かを一覧化して」
- 既存の静止画+サイズ推測(ヒューリスティック)方式の注釈で「枠が要素とズレる」と言われたとき → この方式に置き換える

## 前提・制約

- **Claude Design MCPコネクタが接続・認可済みであること**(`mcp__claude-design__*`が呼べる状態)。これは対話セッションでのOAuth認可が必要な接続で、未接続の場合はユーザーにclaude.aiのコネクタ設定で接続してもらう必要がある。非対話(ヘッドレス/cron)実行では使えないことがある。
- **対象となる既存プロジェクト+既存の`.dc.html`画面が既にあること**。このスキルは既存のDesign Components画面に注釈を追加するものであり、画面自体を新規デザインするものではない(画面がまだ無い場合は先にデザインを作る必要がある)。
- **検証にはブラウザツール(chrome-devtools MCP等)が望ましい**。無い場合、`render_preview`が返す`open_url`をユーザーに渡して目視確認してもらう(`serve_url`は自分のブラウザツール専用で、ユーザーには絶対に渡さない)。
- 対象はClaude Designプロジェクト内の`.dc.html`。仕様書ページは**同じプロジェクト内に置く同居ファイル**として作る(`iframe src="./対象.dc.html"`が同一オリジンで読めることが前提。別プロジェクトを跨いだiframeはクロスオリジンになりDOM測定ができない)。
- エンジニアリングドキュメント全体(要件一覧・ER図・アーキテクチャ等)をこの方式でClaude Design側に丸ごと移すのは非推奨。gitリポジトリ側で管理すべき文書(basic-design-ui.html等)はそのまま残し、**「コンポーネント+その場の要素注釈」だけ**をこの方式でDesign側に置くハイブリッド構成が良い(git側はdiff/レビュー/検索性、Design側はDOM実測によるズレ無し、を両取りする狙い)。
- `.dc.html`の仕様(x-dc/support.js/テンプレートホール等)は`get_claude_design_prompt`で読める設計システムプロンプトが正。テンプレートホール`{{ }}`はドット参照のみ(三項演算子・式は書けない) — クラス名の出し分け等は`renderVals()`側で文字列を組み立てて渡す。

## 手順

### 1. 対象ファイルと採番対象を決める

- `list_files`でプロジェクト内の`.dc.html`一覧を確認。対象画面(例: `Dashboard.dc.html`)を`read_file`で読む。
- テキスト版の画面仕様(screen-specifications.md等)が既にあれば、そこに書かれた「#/要素/種別/動作/テキスト」をそのまま使う(採番し直さない)。無ければ画面を見て自然な読み順(左上→右下、ヘッダー→本文→フッター)で新規に採番する。
- **複数フレーム/キャンバスの画面**(1ファイルに複数の状態・ステップが並ぶデザイン)の場合、番号をフレームごとにリスタートしない。全フレームを通してグローバルに一意な番号を振る(例: フレーム1が1〜7、フレーム2が8〜19、…)。`data-spec-id`は「1つのIDに対して1つの代表要素」が前提なので、番号の再利用は禁止。

### 2. 対象の`.dc.html`に`data-spec-id`を追加する

- 各採番要素に対応する実DOMノードに`data-spec-id="N"`をそのまま追加する。既存のclass/style/挙動は変更しない。
- 対応するタグが無い(生テキストが`{{ }}`で直接埋め込まれているだけ等)場合は、レイアウトに影響しない`<span data-spec-id="N">…</span>`で軽く包む。
- `<sc-for>`の中の繰り返し要素(例: 一覧の行、複数チップ)には同じ`data-spec-id`をそのまま付けてよい。実測側は最初にDOMで見つかった1個だけを代表として使う(重複除去は仕様書ページのJSが自動で行う)。
- `finalize_plan`→`write_files`で書き込む。`if_match`に直前の`read_file`/`list_files`のetagを渡す。

### 3. 仕様書ページ(`<画面名> Spec.dc.html`)を作る

- `assets/spec-page-template.dc.html`をベースに、以下のプレースホルダを置換して新規作成する:
  - `__SCREEN_TITLE__`: 表示用タイトル(例: `S01 ダッシュボード`)
  - `__TARGET_FILE__`: iframeで読み込む対象ファイル名(例: `Dashboard.dc.html`)
  - `__IFRAME_WIDTH__`: iframeの「地の幅」(px)。対象画面の実際の想定幅に合わせる(目安: フルページ画面1300、モーダル800〜1000、複数フレームのcanvas画面はフレーム全体を並べた合計幅)。この幅を基準に、画面側の表示倍率(20%〜100%)が計算される。
  - `__IFRAME_HEIGHT__`: iframeの「地の高さ」(px)。対象画面の想定コンテンツ高さに合わせる(目安: フルページ画面900、モーダル600程度)
  - `__ELEMENT_COUNT__`: 採番した要素の総数
  - `__SPEC_LABELS_JS__`: `{1:'1. 要素名', 2:'2. 要素名', ...}` 形式のJSオブジェクト(ホバー吹き出し用の短い説明)
  - `__SPEC_TABLE_ROWS__`: `assets/spec-table-row-template.html`を要素数分複製して埋めた`<tr>`群
- テーブル行の`__TYPE_CLASS__`/`__TYPE_LABEL__`は種別に応じて選ぶ: `t-view`(表示のみ)/`t-click`(クリック可能)/`t-input`(入力)/`t-select`(選択)。`__NATURE_CLASS__`/`__NATURE_LABEL__`は`stat`(静的)/`dyn`(動的)。
- 対象ディレクトリに`support.js`が無ければ`create_support_js`を先に呼ぶ。
- `finalize_plan`(対象.dc.html書き換えと同時でよい)→`write_files`。

### 4. 検証する

`render_preview`→`serve_url`をブラウザツールで開き:
1. ページ下部の「検出済み要素: N / N」が要素総数と一致するか確認。一致しない場合、`<sc-if>`で条件付き非表示になっている要素(初期状態でfalseなど)に採番していないか確認する。
2. 数値チップをホバーし、破線枠が対象要素にきっちり(パディング分だけ広めに)フィットしているか確認。
3. **対象プロジェクトに`tokens.css`があるか確認する。** テンプレートは7行目で`<link rel="stylesheet" href="./tokens.css">`を読み、全スタイルが`--line` `--panel` `--ink-soft` `--ink-faint` `--signal` `--paper` `--font-mono`に依存している。無いと仕様書ページが素の見た目になる(その場合はトークンを定義するか、テンプレート側に既定値を持たせる)。
4. デザイン変更への追従を確認したい場合、対象`.dc.html`側の何か(サイズ等)を変えて再読み込みし、仕様書ページ側を一切触らずに枠が追従するかを見る(確認できたら元に戻す)。
5. パディングスライダー・採番チップ表示トグルが効くか確認。
6. 中央の境目(`.spec-divider`)をドラッグして左右の幅比を変え、表示倍率(ツールバー右端の%表示)が20%〜100%の範囲で追従し、チップが引き続き実要素にフィットしているか確認する(スケール後もズレていないか)。

### 5. 全画面への展開

1画面で確認が取れたら、他の画面にも同じ手順(2〜4)を1画面ずつ繰り返す。まとめて全部に`data-spec-id`を先に振ってから仕様書ページを一括生成するより、**1画面ずつ通しで検証してから次に進む**方が、番号の対応ミスに早く気づける。

## この方式で確定している見た目・挙動の仕様(変更しない限りこのまま複製する)

- 破線枠のパディングは既定**12px**(スライダーで0〜32pxに調整可能)。枠は実要素そのものではなく一回り外側に描くことで、小さい要素(ドット等)の採番チップが要素に重ならないようにしている。
- 枠を描くレイヤーの外側に**28pxの余白を持つ親コンテナ(`.spec-frame-outer`)**を必ず置く。パディングを広げた枠が画面端の要素で画面外に出て見切れるのを防ぐため。
- 採番チップは既定で常時表示、破線枠自体は**ホバー/アクティブ時のみ**表示(Chrome DevToolsの要素インスペクタ風)。
- いずれかのチップをホバー/クリックすると、そのチップだけ強調され、**他の全チップは不透明度20%に薄くなる**(密集領域での視認性確保)。
- チップクリックで対応するテーブル行にスクロール(`scrollIntoView`は使用禁止 — Claude Designのシステムプロンプトで明示的に禁止されているため)。**テーブル側カラム要素の`scrollTo({top, behavior:"smooth"})`**で実装する(2カラムが独立スクロールなので、`window.scrollTo`ではなくカラム要素に対して呼ぶ)。テーブル行のホバーでも対応チップがハイライトされる(双方向)。
- 実測は初回マウント時 + `resize`イベント + iframeの`load`イベント + 1秒ごとのポーリングで再計算する(デザインの継続的な変更に強くするため)。
- 採番チップの全体表示/非表示トグルをツールバーに置く(スクリーンショット代わりに素の画面を見たいときのため)。
- 画面(iframe)と要素テーブルは左右2カラムで、それぞれ`overflow:auto`により**独立してスクロール**する(縦に長い画面でも一望性と表の同時参照を両立するため)。
- 2カラムの境目(`.spec-divider`)は**ドラッグでカラム幅を変更**できる。画面側はテーブル側の最小幅(320px)を潰さない範囲でしか広がらない。
- 画面側は`__IFRAME_WIDTH__`/`__IFRAME_HEIGHT__`を「地の大きさ」として固定し、実際の表示は`.spec-frame-wrap`に`transform:scale()`をかけて**現在のカラム幅に収まるよう20%〜100%の範囲で自動縮小/拡大**する(下限20%より狭いカラム幅ではみ出し・横スクロールが出るのは仕様)。採番チップは`.spec-frame-wrap`の子要素なので、この拡大縮小に自動的に追従し、iframe内実測(`getBoundingClientRect()`は常にiframeの地のピクセル値を返す)のロジックは変更不要。

## 既知の注意点

- 状態が非同期に更新されるため、プログラムからチェックボックス等をクリックした直後に即座にDOM状態を読むと古い値が返ることがある(実際のユーザー操作では問題ない)。検証時は少し待ってから確認する。
- `checked="{{ showChips }}"`のような真偽値のwhole-value属性は、`onChange`(または`onClick`)ハンドラを必ずペアで渡す。ハンドラが無いままcheckedだけ渡すと操作不能になる。
