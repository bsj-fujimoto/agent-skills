# セッションの振り返りHTML

長い会話を、**あとから来た人が5分で追える1枚**にする。
成果物は「議事録」ではなく「**どう進めたかの地図**」。

## 最初に決めること: このセッションに記録を残してよいか

**残したくないなら、別プロセスに投げる。** これが既定。

```bash
"$SKILL_DIR/scripts/detached.sh" <セッションID> <出力先.html>
```

呼ばれた側が自分で SKILL.md を読み、最後まで作って出力パスを返す。
`claude -p` / `cursor-agent -p` / `codex exec` のうち使えるものを自動で選ぶ。

### なぜ既定なのか

このスキルを使いたい場面は、たいてい**参考にしたい良いやり取りが
行われたセッション**。そこで `/session-recap` を叩くと、
HTMLを作る作業（ログを読む・JSONを組む・ビルドし直す）が
**そのセッションのログに残ってしまう**。

振り返る価値のある会話ほど、末尾に作業ログがぶら下がるのは惜しい。
そのセッション自体が次の資料になるなら、なおさら。

| | 記録の残り先 |
|---|---|
| **別プロセス**（既定） | 呼ばれた側の新しいセッション。**元は無傷** |
| サブエージェント | 親のログの `subagents/` 配下。本流には出ないが同じセッションの管理下 |
| そのまま実行 | **いまのセッションに全部残る** |

### そのまま実行してよい場合

- 使い捨てのセッション（この作業のためだけに開いた）
- **いまの会話の中身が材料として要る**とき。
  別プロセスからは「ログに書かれたこと」しか見えない。
  この場で口頭で決めた判断や、まだログに落ちていない文脈が
  要約に要るなら、自分でやるしかない

迷ったら聞く。「このセッションに作業ログを残してよいですか」の一言で済む。

## そもそもスキルが要るのか

**短いセッションなら、ログを読む必要はない。** 会話が全部見えているなら、
そのまま要約して `build.py` に渡せばよい。

ログを読みにいくのは次の場合。

| 状況 | なぜ見えている分では足りないか |
|---|---|
| **compact が起きた** | 前半が文脈から消えている。ログにしか残っていない |
| **別のセッションをまとめる** | そもそも見えていない |
| **長いセッション**（数十ターン以上） | 読み返しに文脈を使い切る |
| **ツール実行回数を数えたい** | 体感では数えられない。ログを数えるしかない |

判断の目安は **compact の有無**。起きていればログを読む。
起きておらず全部見えているなら、手順1を飛ばして手順2から始めてよい。

**ログを読むなら、サブエージェントに投げるのが既定**（本文は数十万字になる）。
判断基準は手順1にある。

**段階分け・要約・HTML生成（手順2〜5）はどちらの場合も同じ**で、
そこがこのスキルの本体。

## 前提

ログの読み出しは**そのつど自分で書く**のが基本。
形式が JSONL でも SQLite でも、構造を1回見れば数行で取り出せる。
このスキルは Claude Code の分だけ、書かずに済むよう用意してある。

段階分け・要約・HTML生成（手順2〜5）はログの出どころに依存しない。

## 大原則

**ログを写すのではなく、意味を取り出す。**

生ログをそのまま並べても読めない。やることは3つ。

1. 全ターンを読んで、**進め方の段階**（フェーズ）を自分で見つける
2. 各ターンを「**人間は何を求め、AIは何をしたか**」の2文に圧縮する
3. 冒頭に、その段階が**どういう順序でつながっていたか**の図を置く

## 手順

### 0. スキルの場所を押さえる

このスキルは `~/.claude/skills/` 以外（プロジェクト配下や別エージェント）にも入る。
**パスを決め打ちにせず**、最初に一度だけ実体の場所を求めておく。

```bash
SKILL_DIR=$(dirname "$(find .claude/skills .agents/skills ~/.claude/skills ~/.agents/skills \
  -name SKILL.md -path '*session-recap*' 2>/dev/null | head -1)")
echo "$SKILL_DIR"
```

プロジェクト配下を先に探し、無ければグローバルに落とす。
シンボリックリンクで入っていることもあるが、`find` は実体まで辿れるのでそのまま使える。
以降の `$SKILL_DIR` はこの値。見つからなければ、このスキルが置かれている
ディレクトリを直接指定する。

### 1. 材料をそろえる

**まず、いま見えている会話で足りるかを考える。**
足りるなら何も読まずに手順2へ。ログを読むのは足りないときだけ。

#### ログを読むなら、まず委譲を検討する

ログの本文は**数十万字**になる（72ターンのセッションで19万字）。
これを自分で読むと、対話の続きに使うコンテキストを食い潰す。

**別のセッションをまとめるときは、必ずサブエージェントに投げる。**
いまの対話と関係ない19万字を自分に入れる理由がない。

| 状況 | どうするか |
|---|---|
| **別のセッション**をまとめる | サブエージェントに委譲（手順1〜4を任せる） |
| **いまのセッション**で compact 済み | 委譲を推奨。ただし本人しか知らない文脈があるなら自分で読む |
| **いまのセッション**が短い | 委譲不要。手順1を飛ばす |

委譲するときは「段階のリストだけ返す」と明示する。
そう言わないと会話の中身を貼って返してきて、節約にならない。

```
セッション <ID> を読んで、進め方の段階に分けてください。

1. python3 <SKILL_DIR>/scripts/extract.py <ID> /tmp/turns.json
2. 出力を全部読む（数十万字あるので分割してよい）
3. 目的で5〜8段階に分ける。動詞で終わる名前にする
   （「調査フェーズ」のような、どこにでも当てはまる名前は禁止）

報告は段階のリストだけ。id / 名前 / ターン範囲 / 一言（1文）。
会話の中身や長い引用は返さないこと。
```

戻ってきた段階の骨格に、手順4でターンの中身を肉付けする。
ターン本文が要るなら `/tmp/turns.json` を必要な範囲だけ読めばよい。

**フォークやワークツリーは効かない。** それが隔離するのはファイルの変更で、
このスキルはリポジトリを書き換えない（読んで HTML を1枚出すだけ）。
汚しているのはコンテキストなので、隔離する先はプロセスであってファイルではない。

#### 自分で読む場合

**自分のログを自分で読む。** 場所と形式は自分が知っているはずで、
知らなくても1回見れば分かる。

```bash
# 1. 場所を確かめる（Claude Code なら ~/.claude/projects/<プロジェクト>/<セッションID>.jsonl）
ls -t ~/.claude/projects/*/*.jsonl | head -3

# 2. 構造を1行だけ見る
head -c 800 <ログのパス>

# 3. 見た構造に合わせて、その場で取り出す
```

JSONL なら `jq`、SQLite なら Python の `sqlite3`（標準ライブラリ）で読める。
**事前に用意されたパーサーは要らない。** 構造を見てから書くほうが速く、確実。
書き方と形式ごとの罠は `references/reading-logs.md`。

Claude Code の場合だけ、書かずに済むよう用意してある。

```bash
python3 "$SKILL_DIR/scripts/extract.py" <セッションID> /tmp/turns.json
python3 "$SKILL_DIR/scripts/extract.py" --list        # 一覧
```

これが有り難いのは形式を吸収するからではなく、**何を捨てるかを知っている**から。
生ログには人間が打っていないものが大量に混ざる。

| 捨てるもの | 中身 |
|---|---|
| スキル本文の展開 | `/xxx` を打つと数千字の定義が「人間の発言」として入る |
| システム注入 | `<system-reminder>` `<local-command-stdout>` |
| サブエージェント内部 | `isSidechain: true` の往復 |
| 引き継ぎ要約 | compact 時に注入される前回までのまとめ |

**自分で読むときも、同じものを捨てる。** ここを素通りすると
「ユーザーが長文の指示を出した」ように見えて、実態とずれる。
完了通知だけは「AIが自発的に動いた区切り」として残す価値がある。

### 2. 段階に分ける

ここがこのスキルの本体。**ツールの種類ではなく、目的で切る。**

| 良い切り方 | 悪い切り方 |
|---|---|
| 設計書をつくる → 未決を聞く → 手分けして書く | 調査フェーズ → 実装フェーズ → 確認フェーズ |
| 動詞で終わる、その回に何を達成したかが分かる | どのセッションにも当てはまり、何も言っていない |

- **5〜8個**に収める。多いと図が読めない
- 時間順に並べる。ただし**何度も割り込む段階**（レビュー・手戻りなど）があれば
  それも1つの段階にし、`when` に「最後まで繰り返し」と書いて図の説明で触れる
- 各段階の `detail` には**数字を入れる**。「162行の関数を8分割」は伝わるが
  「リファクタリングした」は伝わらない

### 3. 反復を見つける

段階の下に、**全体を貫いていた短いループ**があれば書く（3〜5歩）。
「問いが来る → 実装を読む → 食い違いが出る → 直す → 次の問い」のような、
そのセッションの**進み方そのもの**。

無理に作らない。見当たらなければ `loop` を `null` にすれば枠ごと消える。

### 4. ターンを圧縮する

**全ターンを載せない。** 流れが分かる回だけ選ぶ（目安: 元の6〜8割）。
落とすのは、単なる相槌・完了通知の連続・同じ作業の続き。

書き方:

- `user` — **口調を残す。** 「後方互換性を意識した設計になっていますか？」を
  「後方互換性について質問」に直さない。生の言葉が場の緊張を伝える
- `ai` — **何を調べて何が分かったかを書く。** 「修正しました」ではなく
  「実装を確認すると無条件に1つのステートマシンを起動しており、既存のキュー残が落ちる危険があると判明」
- 流れが変わった回には `pivot: true`。セッション全体で**2〜4回**まで。
  多用すると意味が消える

### 5. 組み立て

`references/data-schema.md` の形で JSON を書き、流し込む。

```bash
python3 "$SKILL_DIR/scripts/build.py" /tmp/recap.json <出力先>.html
```

`build.py` は書き出したあと**自分で描画して確かめる**（構文・データ復元・件数）。
`自己チェック: OK` が出れば、ブラウザで開いても崩れていない。

止まる場合はデータ側の問題なので、メッセージのとおり直す。

- 未定義の段階を参照している
- 必須キーが無い
- 描画件数が JSON と合わない

`</script` や `<img>` を含む本文を書いても安全（無害化・エスケープされる）。
要素はJSで組み立てるので、**出力HTMLを grep しても件数は数えられない**（0件や1件に見える）。
数えたいときは `build.py` の出力を見る。

### 6. 開く

```bash
open <出力先の絶対パス>
```

コンテナ内など `open` が効かない環境なら、
**ホストから開けるパスにもコピーして**（例: リポジトリの `.tmp/`）そのパスを伝える。
その場合は `.gitignore` されているかを確認する。

## 出力ルール

- **ローカルファイルとして生成する。** Artifact として公開しない
- 保存先はスクラッチパッド（無ければ `/tmp`）。指定があればそちらに従う
- ファイル名は `session-recap-<内容のスラッグ>.html`
- 最後に絶対パスと、要点3行を伝える

## つまずきやすいところ

| 症状 | 原因 |
|---|---|
| ページが途中で切れる | 本文の `</script`。`build.py` を通していない |
| grep したら件数が1件だった | 要素はJSで作られる。`build.py` の出力を見る |
| フィルタを押すと空になる | `turns[].phase` が `phases[].id` に無い |
| 図が「調査→実装→確認」になった | 目的でなくツールで切っている。2をやり直す |
| どのターンも同じに見える | `ai` に「修正しました」しか書いていない。何が分かったかを書く |
